Update the public function `xrspatial.rasterize.rasterize` so eager NumPy rasterization returns the same raster values and requested output dtype as before while reducing avoidable peak memory. With the default `float64` dtype, callers should not pay for an additional full-output-size copy solely for final dtype conversion. On eager CPU/NumPy rasterization, order-insensitive merges such as `max`, `min`, `sum`, `count`, and user callables should avoid the 8-byte-per-pixel owner-order memory cost, while order-dependent merges such as `first` and `last` must still resolve overlaps with their existing semantics. Calls with a non-default dtype must continue returning that requested dtype with values cast consistently with the existing API, and all supported merge modes, fill handling, bounds, shape, and all-touched behavior must preserve the same rasterization results.
